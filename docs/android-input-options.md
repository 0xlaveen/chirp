# Android input options for Chirp

Research checked 2026-10-17 against Android 16 and 17 sources, the API 37 documentation, Samsung support, and voice-IME prior art. This is a source review plus JVM validation, **not a Galaxy Z Fold 8 hardware result**. No device/adb access was used. One UI menus vary with region, keyboard version, carrier and system update.

## Recommendation and what ships

**Primary: an explicitly enabled accessibility floating microphone (C), with Samsung Keyboard left selected.** It supplies the missing entry point without depending on a vendor voice picker. **Fallback: Chirp Keyboard selected through Android's keyboard picker**, started with a manual tap or press-and-hold. Path A — the `voice` subtype, its auto-start on launch and the automatic `switchToPreviousInputMethod()` return — is **retired** (2026-10-23): `res/xml/input_method.xml` declares only a `keyboard` subtype, and the old voice-only service lives on only in test sources. There is no supported way for a sideloaded app to inject a button into Samsung Keyboard itself.

Do not tell the operator that enabling Chirp as a keyboard will make Samsung's mic use it. Samsung's own instructions describe only Samsung voice input and Google Voice Typing. The FUTO Voice Input project's compatibility documentation explicitly reports Samsung's two-provider restriction and Gboard's Google-only routing. This corroborates the choice to provide our own button. [Samsung keyboard settings](https://www.samsung.com/us/support/answer/ANS10001592/), [FUTO's compatibility documentation](https://github.com/futo-org/voice-input/blob/master/README.md).

C is optional because accessibility is a broad system capability even when used narrowly. Unsupported/custom editors and policy restrictions must have a usable fallback. In particular, Android 17 Advanced Protection restricts accessibility access to verified accessibility tools. Chirp declares `isAccessibilityTool=false` honestly; it does not relabel itself to evade this restriction. Use the IME if accessibility cannot be enabled. [Google's October 2026 Advanced Protection announcement](https://blog.google/security/android-advanced-protection-updates/).

| Path | Existing keyboard | Reliability / restrictions | Latency | Battery while idle | Privacy / insertion |
| --- | --- | --- | --- | --- | --- |
| A: voice IME shortcut (retired) | Would have returned after a temporary switch | Good with a cooperating keyboard; Samsung/Gboard do not offer arbitrary third-party voice providers | Immediate capture on panel launch; TLS/model latency remains | No mic or stream while idle; bounded health check on panel show | Direct `InputConnection`, composing partials where supported; final-only fallback; no screen access |
| B: `RecognitionService` | Only if the keyboard actually calls the selected recognizer | Valid Android API; changing default does not override an explicitly chosen service or on-device recognizer; One UI may hide the chooser | Similar streaming costs plus Binder callbacks; client controls initiation/stopping | System may keep a bound provider process; no reason to capture or maintain a socket between requests | Returns hypotheses to caller; caller decides insertion, composing, correction/undo UI |
| C: accessibility overlay | Yes, Samsung or another keyboard stays selected | Requires user opt-in, editable accessibility nodes and `ACTION_SET_TEXT`; Android 17 Advanced Protection / managed-device policy may block enabling | Capture starts on press; partials in panel, one checked final insertion | Event-driven bound service remains; no audio, network, FGS, polling, wake lock or repeating animation while idle | Only focused field text/selection in memory; final splices selection into preserved surrounding text; no clipboard/history/logging |
| Keyboard picker fallback | Selects Chirp Keyboard | Most portable for normal editors; password fields refused | Extra user switch, then tap or hold-to-talk | No mic/stream idle; stops on hide | Direct editor connection, same cancellation and raw replacement protections |

Latency and battery entries are architectural expectations, not measured numbers. All Chirp paths depend on the paired Mac and Tailscale; none are phone-local/offline speech recognition. Existing debug timings are numbers only. Hardware radio, OEM scheduling and engine warmup need measurement by the operator.

## A. Voice IME from another keyboard's microphone (retired)

**Retired 2026-10-23.** The `voice` subtype, its auto-start on subtype launch, the `switchToPreviousInputMethod()` return and the auto-return preference never shipped; `res/xml/input_method.xml` declares only a `keyboard` subtype, the full keyboard always stays selected after a final, and the old voice-only implementation survives only in test sources (`LegacyVoiceImeService`, not registered or shipped). The research below is retained as prior art.

A voice subtype is discovery metadata, not a role assignment. The design retained both `voice` and `keyboard` subtypes in `res/xml/input_method.xml`; the shipped input method declares only the `keyboard` subtype. An enabled IME can call `InputMethodManager.getShortcutInputMethodsAndSubtypes()` and switch to a returned `InputMethodInfo`/subtype using its IME token. Historical AOSP LatinIME's `SubtypeSwitcher.updateShortcutIME` and `switchToShortcutIME` show this mechanism. It is useful prior art, **not proof of present Gboard internals**. [LatinIME source](https://android.googlesource.com/platform/packages/inputmethods/LatinIME/+/1109ab9c65d06bc5c7003e31ce8bee90a2dfda24/java/src/com/android/inputmethod/latin/SubtypeSwitcher.java).

The Android 16 and Android 17 implementations of `getShortcutInputMethodsAndSubtypes()` sort enabled IMEs with system packages first, scan for a `voice` subtype, and return a **single** map entry. They do not provide an arbitrary user-selected list of all third-party voice IMEs. Chirp may be eligible, but an installed Google/system voice IME generally wins this scan. Older AOSP versions had different, more restrictive fallback logic; do not use an old system-IME-only implementation to describe Android 16/17. [Android 16 implementation](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/android16-release/core/java/android/view/inputmethod/InputMethodManager.java), [Android 17 implementation](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/android17-release/core/java/android/view/inputmethod/InputMethodManager.java).

Samsung documents **General management → Keyboard list and default**, enabling Google Voice Typing and the navigation-bar keyboard button, then **Samsung Keyboard → Voice input**, choosing Samsung or Google. That menu is not a general `RecognitionService` or IME component picker. FUTO's compatibility findings explicitly confirm Samsung/Gboard restrictions; FUTO lists HeliBoard, FlorisBoard, AnySoftKeyboard, Unexpected Keyboard and AOSP Keyboard among compatible alternatives. We do not require the operator to change keyboards. [Samsung](https://www.samsung.com/us/support/answer/ANS10001592/), [FUTO](https://github.com/futo-org/voice-input/blob/master/README.md).

Gboard's help explains using its own mic, including device-dependent advanced voice typing; it offers no documented third-party provider selector. Installing a voice IME therefore does not establish that Gboard will invoke it. [Gboard help](https://support.google.com/gboard/answer/2781851).

Retired implementation: `onCurrentInputMethodSubtypeChanged` remembered voice mode; the first `onStartInputView` while visible started recording once. Fold/view recreation did not start a second utterance. The panel was never fullscreen. Final commits returned with `switchToPreviousInputMethod()` (picker if no previous IME). Corrected output retained the five-second “Use raw” opportunity before returning. Cancel on a voice launch returned when auto-return was enabled. A regular keyboard-mode invocation waited for tap/hold. Permission, pairing and password checks ran before capture. Composing rejection left live text in the panel and still attempted a single final commit. The shipped keyboard keeps the tap/hold start, permission/pairing/password gates and the Use raw window; it never switches away from the keyboard and never auto-starts.

## B. System speech recognizer

A provider extends `RecognitionService`, advertises `android.speech.RecognitionService`, protects its binding with `android.permission.BIND_SPEECH_RECOGNITION_SERVICE`, and supplies `android.speech` metadata pointing at `<recognition-service android:settingsActivity="…" android:selectableAsDefault="true"/>`. The service implements start/stop/cancel, terminates each request with results or error, and releases recorder/buffers/socket on disconnect/cancel. API references document the stateless provider contract and callback attribution/permissions. [RecognitionService](https://developer.android.com/reference/android/speech/RecognitionService), [Callback](https://developer.android.com/reference/android/speech/RecognitionService.Callback).

Default recognition selection is distinct from the default keyboard, default voice IME and digital assistant. Android's `VoiceInputHelper` discovers valid recognition-service metadata, filters `selectableAsDefault`, and reads `Settings.Secure.VOICE_RECOGNITION_SERVICE`. The setting is managed by the system/user, not an ordinary app writing secure settings. `SpeechRecognizer.createSpeechRecognizer(context)` uses system selection; a client can instead specify a `ComponentName`, and on-device recognizer creation is a separate route. [Android 17 Settings source](https://android.googlesource.com/platform/packages/apps/Settings/+/refs/heads/android17-release/src/com/android/settings/language/VoiceInputHelper.java), [SpeechRecognizer API](https://developer.android.com/reference/android/speech/SpeechRecognizer).

`RecognitionService.Callback.partialResults(Bundle)` maps Chirp hypotheses into `SpeechRecognizer.RESULTS_RECOGNITION`; clients requesting `RecognizerIntent.EXTRA_PARTIAL_RESULTS` receive `RecognitionListener.onPartialResults`. Partial delivery may occur zero, one or many times, and applications decide whether/how to display or compose it. On final, call `results`; on stop, release the mic before waiting for the Mac's final. Honor permission attribution, binder death, concurrent-client refusal, unsupported intents/languages, and offline/on-device requests honestly. A Mac-over-network recognizer must not advertise itself as an on-device engine. [Partial-results contract](https://developer.android.com/reference/android/speech/RecognitionListener#onPartialResults(android.os.Bundle)).

One UI's **Apps → Choose default apps → Digital assistant app** selects an assistant; Samsung's published instructions do not say this selects an arbitrary keyboard transcription engine. Some builds expose a separate Voice input/default recognizer page; others do not. `Settings.ACTION_VOICE_INPUT_SETTINGS` is the public settings action, but Android explicitly says a matching Activity may be absent. One UI 8.5 users also report not finding a provider chooser; that is an observation from a Samsung-hosted user report, not an OEM API guarantee. [Samsung assistant instructions](https://www.samsung.com/us/support/answer/ANS10004856/), [settings action](https://developer.android.com/reference/android/provider/Settings#ACTION_VOICE_INPUT_SETTINGS), [One UI 8.5 report](https://us.community.samsung.com/t5/Questions/Voice-Typing-Engine-Missing-in-One-UI-8-5-Gboard-Still-Uses/td-p/3456938).

**Not shipped in this change.** B would be a new external-client/permission-attribution contract, not a cheap reliable Samsung integration. It would not restore a selector Samsung does not expose, override vendor mic routing, or give us control of a client's raw-undo UI. C plus the IME solves the operator's entry point without silently replacing speech recognition for unrelated apps. A future B can reuse the single-utterance streaming controller after dedicated client-contract tests.

## C. Accessibility floating microphone

### Focus, insertion and privacy

`ChirpAccessibilityService` uses `TYPE_ACCESSIBILITY_OVERLAY` with `FLAG_NOT_FOCUSABLE` and `FLAG_NOT_TOUCH_MODAL`. The keyboard/editor retain input focus; no `SYSTEM_ALERT_WINDOW` grant is needed for this accessibility window type. The overlay is an edge-docked bubble until invoked, then a compact Pond voice panel (see [The bubble](#the-bubble) below). Layout uses current window metrics and the focused field's screen bounds; configuration changes recreate only the controls while keeping the utterance. [AccessibilityService](https://developer.android.com/reference/android/accessibilityservice/AccessibilityService), [window types](https://developer.android.com/reference/android/view/WindowManager.LayoutParams#TYPE_ACCESSIBILITY_OVERLAY).

Only focus, focused-field text/selection and window-transition events are subscribed, with a 100 ms notification timeout. No `TYPE_WINDOW_CONTENT_CHANGED`, `typeAllMask`, interactive-window retrieval flag, screenshot API, root-tree traversal, screen scraping, periodic focus scan or event logging is used. Event source nodes are considered; a single `findFocus(FOCUS_INPUT)` query handles connection/window transitions. Broad `canRetrieveWindowContent` is required by Android for node access, but the implementation narrows its use. Accessibility still keeps an event-driven system binding/process while enabled; claiming literally “no service exists while idle” would be inaccurate. [Accessibility configuration](https://developer.android.com/reference/android/accessibilityservice/AccessibilityServiceInfo).

On a user start, `FocusedInsertion` snapshots only the chosen editable node's current text and selection (max 100,000 characters). Password, disabled and non-editable fields get no bubble at all. A field with an unknown selection, more than 100,000 characters or no `ACTION_SET_TEXT` is **copy mode**: the bubble still shows, with a clipboard badge, and the final goes to Ready to copy instead of the field. Partials stay in the panel, so cancellation cannot modify the editor. Final insertion refreshes and verifies identity/focus/text/selection, constructs `prefix + final + suffix` around the original selection (including reversed selections), calls one `ACTION_SET_TEXT`, then moves the caret. A changed editor is refused, and **the final is never dropped**: a refused, failed or moved-away write puts it in the panel's **Ready to copy** state (text in memory only, cleared on Done, ✕, screen off, service destroy or after 2 minutes). Corrected output allows one verified raw replacement for five seconds; later user edits, focus/window changes, hide/cancel, screen-off, timeout and service destruction clear it. The clipboard is used **only on a tap of Copy**, never automatically, and the clip is marked `ClipDescription.EXTRA_IS_SENSITIVE`; Samsung's clipboard history may still keep it, which the Settings note says. **Open in Scratchpad** hands the text over through in-process memory, never an Intent extra. [Node actions and arguments](https://developer.android.com/reference/android/view/accessibility/AccessibilityNodeInfo), [sensitive clipboard content](https://developer.android.com/develop/ui/views/touch-and-input/copy-paste#SensitiveContent).

`ACTION_SET_TEXT` is necessarily a read/verify/write operation, not an atomic transaction with another app. It cannot guarantee safety against a simultaneous app-side edit between refresh and action. Custom rich-text/WebView editors can expose incomplete or misleading nodes; there the final waits in Ready to copy. It also drops the other keyboard's composing state and rich spans; that is existing behaviour, and Chirp keeps refusing to write a field that changed. No claim that the bubble works in every app is made.

Field contents stay on the phone; only dictated audio and existing correction opt-in metadata go to the Mac. The raw/final text and field snapshot are transient memory, never preferences, saved UI state, notifications or logs. Pairing tokens remain AES-GCM encrypted using Android Keystore; QR/deep-link input is validated, masked, not saved across recreation and removed from the incoming Intent. Both panels and setup show the debug-retention warning if the authenticated server reports it. That warning means the **Mac** may retain recordings; the phone does not persist them.

### Microphone on Android 14–17

A background service does not get microphone access merely because `checkSelfPermission(RECORD_AUDIO)` returns granted. Android 14+ validates while-in-use access at microphone foreground-service creation. Background FGS-start exemptions and while-in-use exemptions are separate. An overlay grant alone is not a general microphone exemption. The public guide lists system starts, qualifying notification/widget interactions, a PendingIntent from another visible app, device owners, VoiceInteractionService and privileged background-activity starters; it does **not** list a blanket “every accessibility app” exemption. [FGS restrictions and exemptions](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start), [microphone service type](https://developer.android.com/develop/background-work/services/fgs/service-types#microphone).

There is relevant AOSP evidence for a **system-bound, enabled** accessibility service: both Android 16/17 `AccessibilityServiceConnection.bindLocked` use `BIND_FOREGROUND_SERVICE_WHILE_AWAKE`, `BIND_ALLOW_BACKGROUND_ACTIVITY_STARTS` and `BIND_INCLUDE_CAPABILITIES`. `ActiveServices.shouldAllowFgsWhileInUsePermissionByBindingsLocked` accounts for a persistent system binder with allowed background-activity starts; app-ops/capabilities are also propagated through the binding. This supports trying a microphone FGS from the enabled service after a user mic press. This is an inference from AOSP binding/capability mechanics, not a universal OEM guarantee. [Android 16 accessibility binding](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/android16-release/services/accessibility/java/com/android/server/accessibility/AccessibilityServiceConnection.java), [Android 17 binding](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/android17-release/services/accessibility/java/com/android/server/accessibility/AccessibilityServiceConnection.java), [Android 16 FGS checks](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/android16-release/services/core/java/com/android/server/am/ActiveServices.java), [Android 17 FGS checks](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/android17-release/services/core/java/com/android/server/am/ActiveServices.java).

Implementation declares `FOREGROUND_SERVICE`, `FOREGROUND_SERVICE_MICROPHONE` and `RECORD_AUDIO`, starts/promotes the accessibility service with `FOREGROUND_SERVICE_TYPE_MICROPHONE` only after the user presses the mic, and uses `AudioSource.VOICE_RECOGNITION`. It never starts at boot or restarts sticky. Promotion happens before constructing capture. Foreground notification offers Cancel and contains no dictated text. Start/promotion denials are caught; the panel says “Android blocked the microphone here” with one action, **Use Quick dictate** (the Scratchpad until Quick dictate ships). Permission grant happens in the visible onboarding Activity. No audio capture is attempted after failed promotion. The recorder releases before STOP; finite connect/final deadlines, bounded zeroed PCM buffers, cancellation and stale-event fencing match the IME guarantees. FGS and network are removed at utterance termination; raw undo has no audio/network resource.

Android 17's audio restrictions and expanded Advanced Protection make opt-in and explicit user initiation especially important. The current implementation does not acquire audio focus, change volume, or play background audio. Hardware acceptance must establish that the enabled service has mic capability on the actual Samsung build. Do not claim a Robolectric test proves OEM app-ops/FGS behavior. [Android 17 behavior changes](https://developer.android.com/about/versions/17/behavior-changes-all), [Advanced Protection](https://blog.google/security/android-advanced-protection-updates/).

### One UI sideload flow

1. Open Chirp → Microphone and allow recording.
2. Input → Enable floating microphone → Accessibility → Installed apps → Chirp floating microphone.
3. If Android shows “Restricted setting”, return to **Settings → Apps → Chirp Keyboard → ⋮ → Allow restricted settings**, authenticate, then return to Accessibility and enable Chirp. The overflow option can appear only after attempting the restricted setting; menus vary by install method and One UI version. Setup links to app details as well as accessibility settings.
4. If policy/Android 17 Advanced Protection prevents activation, use **Enable Chirp Keyboard** and the keyboard picker. No security bypass or accessibility-tool misclassification is implemented.

The user is granting sensitive screen-interaction capabilities; onboarding and the service description explain the narrow field-only use before directing them to the system grant. [Android's restricted-settings instructions](https://support.google.com/android/answer/12623953), [Samsung-hosted restricted-settings report](https://us.community.samsung.com/t5/Questions/Can-use-some-of-my-accessibility-services/m-p/2621343).

### The bubble

#167 made the floating mic a path people would choose. The code lives in `FloatingMicBubble.kt` (the windows), with pure `BubbleGesture.kt` and `BubblePlacement.kt` and the panel's `FloatingMicState.kt`.

- **Look.** A 48 dp `surfaceRaised` disc on a 56 dp touch target, with a 1.5 dp koi ring, the Material Symbols Rounded mic and one soft 3 dp shadow (it floats over other apps). It fades and scales in over 120 ms and fades out over 90 ms; with animations off it shows and hides at once.
- **Gestures** (`BubbleGesture`; the panel's own mic keeps `MicGesture`):

  | Touch | Result |
  |---|---|
  | Up within 250 ms, moved less than 8 dp | Tap: open the panel and dictate (toggle) |
  | Moved more than 8 dp before 250 ms | Drag: no capture, service or mic indicator; snaps to the nearer edge on release |
  | Held still for 250 ms | Hold to talk: confirm haptic, Ripple, one-line partials pill; release stops |
  | Cancel | Cancels a started utterance |

- **Placement** (`BubblePlacement`).
  - It is docked left or right at a remembered height, saved per posture (`cover`/`inner` × `portrait`/`landscape`) as an edge and a fraction, written only on drop.
  - By default it sits on the right edge just above the field's centre.
  - It is nudged vertically off the field so it never covers the text.
  - The panel is at most 360 dp wide, 16 dp from the edges, and above the field when it fits, otherwise below it.
- **Keeping clear of the IME (spike).** The overlay first reads `WindowInsets.Type.ime()` from its window metrics and its own root. Otherwise, with the field in the lower half of the screen, it places the bubble above the field.
  - **Result on the API 37 emulator (Gboard): not determined.** Every focused field in the bubble check sat in the upper half, and the bubble stayed clear of Gboard there.
  - Which rule applies to a low field is unverified on hardware. Both rules are covered by `BubblePlacementTest`, and the device acceptance steps include a low field.
- **WebView.** On the API 37 emulator Chromium reported its textarea as focused while a native field held the input focus, so the service now trusts only the system's input focus. The probe's textarea then got no bubble: Chromium did not report it as the input focus. Rich and web editors otherwise end in Ready to copy when they refuse `ACTION_SET_TEXT`.
- **Hide here.** While dragging, a koi-outlined ✕ sits at bottom centre. Dropping on it hides the bubble for the current app until another app comes to the front. This is session-only state, never persisted.
- **TalkBack.** The bubble is a button: double tap dictates, and its custom actions are **Move to other side** and **Hide in this app**. Hold to talk isn't offered, because the panel's toggle covers it.
- **States.** Connecting → Listening (Ripple, live partials, Stop as a `record` pill, Cancel) → Finishing/Polishing → Inserted. Two other outcomes:
  - **Polished** gets a `moon` chip and **Use raw** with a 5 s bar.
  - **Ready to copy** offers Copy, Open in Scratchpad and Done.
- **Errors** each carry exactly one fix:
  - not paired → Pair computer;
  - microphone denied → Allow;
  - Computer offline → the keyboard's reason with Check again, or "Tailscale is off" with Turn on on a tailnet pairing;
  - FGS start blocked → Use Quick dictate.
- **Window changes.** A window change mid-utterance stops capture, and the final lands in Ready to copy rather than in another app. The lock screen and screen off still discard everything.

## Other entry points

A quick-settings tile or notification action can provide an explicit trigger. Neither grants an `InputConnection` to Samsung's focused editor. They still need C for insertion or must switch to the IME. A tile can open a visible Activity with `TileService.startActivityAndCollapse(PendingIntent)` on modern Android, then start a microphone FGS while visible. A qualifying notification interaction is a documented while-in-use exemption, but maintaining an idle notification solely to get a mic button is a poor default. No boot receiver, permanent notification, polling tile service or overlay-permission workaround is added. [TileService](https://developer.android.com/reference/android/service/quicksettings/TileService), [FGS exemptions](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start).

`RecognizerIntent.ACTION_RECOGNIZE_SPEECH` Activity-based integrations are another opt-in route for apps that launch that intent, but do not inject a provider into Samsung's mic chooser. FUTO's use of both IME and implicit-intent integration is relevant prior art. [RecognizerIntent](https://developer.android.com/reference/android/speech/RecognizerIntent), [FUTO project](https://github.com/futo-org/voice-input/blob/master/README.md).

## Validation and operator acceptance

Automated checks: `cd android && ./gradlew lint testDebugUnitTest assembleDebug assembleRelease` passed on 2026-10-17: lint reported no issues, 124 tests passed and two opt-in live tests were skipped (126 total); both APKs built. The release APK is unsigned without a local keystore. Lint warnings remain errors. Tests use synthetic text, fake capture/transport/editors, Robolectric API 31/37 and native rendering; no live Mac configuration, microphone, device or default-port test server is used. Rendered review assets live in `docs/screenshots/android/` and are under 2 MB total. These cover presentation and lifecycle contracts, not phone battery/latency or One UI permission enforcement.

After the orchestrator installs the APK, the operator should complete the four-step wizard, leave Samsung selected for the bubble, pair by QR and test the native editor. Then check Samsung Notes and a browser field: insert at caret, replace a selection without losing prefix/suffix, cancel, raw/expiry, type/move focus while recording, lock/hide, fold/unfold, stop before the Mac connects, deny/revoke mic permission, and disconnect the network. Check that the mic privacy indicator disappears on every stop/cancel/error. Check the IME fallback (manual start; the voice-subtype auto-start of retired Path A no longer exists); do not spend time looking for a Chirp option in Samsung's documented two-provider picker. Test light/dark, cover/inner screens and enlarged text. Measure actual battery and latency separately; do not enable Mac debug retention just to capture screenshots.

## Keep-my-keyboard setup decisions

Onboarding and Settings → How you dictate now offer Chirp Keyboard or keeping the current keyboard with the optional floating mic. The selection changes setup recommendations, not access to Notes, Scratchpad, History or tiles. The floating mic hides whenever Chirp Keyboard is the selected IME. Its disclosure precedes Android settings; restricted-settings help reacts to an unsuccessful return, because no public API exposes that restriction. Advanced Protection is checked on API 36+ through [AdvancedProtectionManager](https://developer.android.com/reference/android/security/advancedprotection/AdvancedProtectionManager). An enabled protection mode offers the keyboard or continuing without the mic.

A `RecognitionService` is deferred: Samsung and Gboard do not route their mic buttons to an arbitrary recognizer; HeliBoard and FlorisBoard use voice-IME handoff. [FUTO](https://github.com/futo-org/voice-input/blob/master/README.md) uses a voice IME and the recognition Activity intent, not that service. A digital-assistant service is rejected because it replaces the user’s assistant and couples the assistant role to a recognizer ([AOSP](https://android.googlesource.com/platform/frameworks/base/+/master/services/voiceinteraction/java/com/android/server/voiceinteraction/VoiceInteractionManagerService.java)). Voice-only IME remains retired. A dedicated Quick dictate Activity, recognition-intent handler, minimal widget and text Share target are planned in separate work. No outside-IME hardware shortcut is added: filtering all keys would expand Accessibility access.

The direct service-details intent uses AOSP’s [ACCESSIBILITY_DETAILS_SETTINGS action](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/android16-release/core/java/android/provider/Settings.java) and component extra, falling back to the Accessibility list. Restricted-settings menus differ between devices; see [Android help](https://support.google.com/android/answer/12623953).

## Keyboard-free entry decisions (#165 / #168)

Quick dictate is the substitute for Path B: a visible, transient Activity owns one utterance, so no microphone foreground service or Accessibility permission is needed. The Dictate tile and launcher widget copy the final, marked sensitive. Speak buttons that launch `RECOGNIZE_SPEECH` receive their own final through the Activity result. Android can show a chooser alongside Google; selecting Chirp does not change Gboard’s or Samsung Keyboard’s microphone routing. [RecognizerIntent contract](https://developer.android.com/reference/android/speech/RecognizerIntent), [TileService](https://developer.android.com/reference/android/service/quicksettings/TileService).

**Path B: not now.** A `RecognitionService` would reach apps using the default `SpeechRecognizer` only where the system exposes its chooser. It does not supply the voice IME subtype that HeliBoard’s `RichInputMethodManager.switchToShortcutIme` (vendored in `android/keyboard/upstream`) and FlorisBoard use. AnySoftKeyboard has voice-IME and Activity-intent routes. FUTO’s two integrations are a voice IME and an implicit Activity intent. Samsung and Gboard keep their vendor routing. Implementing B would also require one-client refusal, permission attribution, Binder death handling, partials, and honest offline semantics. Revisit only for identified apps using the default `SpeechRecognizer`, or a deliberate new assistant proposal. If revisited, keep `PhoneRecognizer.createOnDeviceSpeechRecognizer` to prevent routing back into Chirp. [FlorisBoard voice subtype](https://github.com/florisboard/florisboard/issues/2684), [voice IME change](https://github.com/florisboard/florisboard/pull/1587), [AnySoftKeyboard discussion](https://github.com/AnySoftKeyboard/AnySoftKeyboard/issues/927), [FUTO integrations](https://github.com/futo-org/voice-input/blob/master/README.md).

**Assistant: rejected.** Becoming the assistant would replace Gemini or Bixby and needs recognizer metadata. AOSP’s assistant selection can fill an empty default-recognizer setting from that package, so an incomplete recognizer could break other apps. This is a source-based inference, not a Samsung hardware result. Samsung documents side-key long press for Gemini/Bixby, and third-party assignment is unverified. The assistant would add a trigger; insertion would still need the floating mic. [VoiceInteractionService](https://developer.android.com/reference/android/service/voice/VoiceInteractionService), [AOSP selection logic](https://android.googlesource.com/platform/frameworks/base/+/master/services/voiceinteraction/java/com/android/server/voiceinteraction/VoiceInteractionManagerService.java), [assistant implementation experience](https://github.com/colonelpanic8/eva/pull/2), [Samsung side-key documentation](https://www.samsung.com/ae/support/mobile-devices/why-does-gemini-work-instead-of-bixby-when-pressing-and-holding-the-side-button-in-one-ui-7/).

### Speak-button extras and ownership

Chirp displays `EXTRA_PROMPT` and returns one result (within any positive `EXTRA_MAX_RESULTS`) with confidence `-1`, meaning unavailable. A polished final is returned directly; insertion and undo belong to the requesting app. Cancel/Back returns `RESULT_CANCELED`; abandoning a displayed error with Done returns the corresponding audio, network or server error. Only `EXTRA_RESULTS` and `EXTRA_CONFIDENCE_SCORES` are returned, never history.

`EXTRA_LANGUAGE` is ignored because the paired Mac’s engine decides the language. `EXTRA_PARTIAL_RESULTS` is ignored because an Activity result cannot stream partials. `EXTRA_PREFER_OFFLINE` does not change processing: speech still goes to the paired Mac; Chirp makes no on-device or offline-recognition claim. [RecognizerIntent extras and results](https://developer.android.com/reference/android/speech/RecognizerIntent).
